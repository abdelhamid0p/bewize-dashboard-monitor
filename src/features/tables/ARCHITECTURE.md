- TABLE ARCHITECTURE DOCUMENTATION
-
- This document describes the scalable, reusable table architecture
- that eliminates duplication and makes adding new tables trivial.

/\*\*

- ============================================================================
- ARCHITECTURE OVERVIEW
- ============================================================================
-
- features/tables/
- ├── components/
- │ ├── DataTable.tsx // Generic table with pagination
- │ └── TableToolbar.tsx // Search + filters toolbar
- ├── hooks/
- │ └── useTableData.ts // Manages all table state & logic
- ├── pages/
- │ └── TablePage.tsx // Main page component (use this!)
- ├── types/
- │ ├── table-config.ts // Strong TypeScript types
- │ └── index.ts
- ├── config/
- │ └── teachers.table.config.example.ts // Example config template
- └── index.ts // Public exports
-
- Each entity (Students, Teachers, Orders):
- features/entity/
- └── config/
-       └── entity.table.config.ts  // Config file + enums
- └── pages/
-       └── EntityTablePage.tsx     // Just imports config & renders TablePage
-
- ============================================================================
- KEY CONCEPTS
- ============================================================================
-
- 1.  TABLE CONFIG (TableConfig<TBackend, TUI, TFilters>)
- - Single source of truth for a table
- - Defines columns, filters, search fields, fetcher, mapper, renderer
- - Fully typed using TypeScript generics
- - Example: STUDENTS_TABLE_CONFIG
-
- 2.  DATA TRANSFORMATION
- - TBackend: Raw API response type
- - TUI: Transformed display type
- - Mapper: TBackend => TUI (handles all business logic)
- - RenderCell: Optional custom JSX per column
-
- 3.  STATE MANAGEMENT
- - useTableData hook manages: data, filters, pagination, search
- - All state changes trigger automatic refetch with new filters
- - Pagination resets when filters/search change
-
- 4.  COMPONENT HIERARCHY
-
- TablePage (main entry point)
-       ├── Header (title + export + settings)
-       ├── TableToolbar (search + filters)
-       └── GenericDataTable
-           └── DataTable (UI component)
-           └── Pagination controls
-
- ============================================================================
- QUICK START: ADD A NEW TABLE
- ============================================================================
-
- STEP 1: Create your backend/UI types
-
- // features/teachers/model/teacher.ts
- export interface TeacherBackend {
-     id: string;
-     firstName: string;
-     lastName: string;
-     email: string;
-     subject: string;
- }
-
- export interface TeacherUI {
-     id: string;
-     name: string;
-     email: string;
-     subject: string;
- }
-
- export interface TeachersFilters {
-     page?: number;
-     size?: number;
-     search?: string;
-     subject?: string;
- }
-
- STEP 2: Create an API fetcher
-
- // features/teachers/api/teachers_api.ts
- export async function fetchTeachers(
-     filters: TeachersFilters
- ): Promise<PaginatedResponse<TeacherBackend>> {
-     // Your fetch logic here
- }
-
- STEP 3: Create the table config (MOST IMPORTANT FILE!)
-
- // features/teachers/config/teachers.table.config.ts
- import { TEACHERS_TABLE_CONFIG } from "@/features/tables";
-
- export const TEACHERS_TABLE_CONFIG: TableConfig<
-     TeacherBackend,
-     TeacherUI,
-     TeachersFilters
- > = {
-     entityName: "Teachers",
-     tableId: "teachers-table",
-     pageSize: 10,
-     columns: [
-       { key: "name", label: "Nom" },
-       { key: "email", label: "Email" },
-       { key: "subject", label: "Matière" },
-     ],
-     filters: [
-       {
-         key: "subject",
-         label: "Matière",
-         type: "select",
-         options: [
-           { label: "Maths", value: "MATH" },
-         ],
-       },
-     ],
-     searchKeys: ["name", "email"],
-     fetcher: fetchTeachers,
-     mapper: (backend) => ({
-       id: backend.id,
-       name: `${backend.firstName} ${backend.lastName}`,
-       email: backend.email,
-       subject: backend.subject,
-     }),
-     renderCell: (teacher, columnKey) => {
-       if (columnKey === "name") {
-         return <strong>{teacher.name}</strong>;
-       }
-       return teacher[columnKey];
-     },
- };
-
- STEP 4: Create the page (one-liner!)
-
- // features/teachers/pages/TeachersTablePage.tsx
- import { TablePage } from "@/features/tables";
- import { TEACHERS_TABLE_CONFIG } from "../config/teachers.table.config";
-
- export const TeachersTablePage = () => (
-     <TablePage
-       config={TEACHERS_TABLE_CONFIG}
-       title="Les professeurs"
-     />
- );
-
- DONE! That's all you need. No pagination logic, no useEffect hooks,
- no filter state management - it's all centralized and reusable.
-
- ============================================================================
- BENEFITS OF THIS ARCHITECTURE
- ============================================================================
-
- ✅ NO DUPLICATION: All table logic lives in ONE place
- - useTableData hook handles pagination, filters, search, refetch
- - GenericDataTable handles rendering
- - TableToolbar handles search/filter UI
-
- ✅ TYPE SAFETY: Full TypeScript support with generics
- - Backend type, UI type, and filters type are all checked at compile-time
- - IDE autocomplete works perfectly
-
- ✅ SCALABILITY: Adding a new table is ~100 lines of code
- - Create types
- - Create fetcher
- - Create config
- - Create page (1 line of code!)
-
- ✅ FEATURE ISOLATION: Each entity owns its config
- - Students config in features/students/config
- - Teachers config in features/teachers/config
- - Orders config in features/orders/config
- - etc.
-
- ✅ CONSISTENT UX: All tables work the same way
- - Same pagination UI
- - Same search/filter behavior
- - Same loading/error states
-
- ✅ MAINTAINABILITY: Changes to table behavior apply everywhere
- - Bug fix in GenericDataTable? All tables get it
- - New feature in TableToolbar? All tables support it
- - No need to update 10 different table containers
-
- ============================================================================
- EXAMPLE: REFACTORING STUDENTS
- ============================================================================
-
- BEFORE (Old Approach):
- - features/students/hooks/useStudents.ts (custom hook)
- - features/students/components/StudentsTableContainer.tsx (custom component)
- - features/students/components/StudentsFilters.tsx (custom filters)
- - features/students/config/student_config.tsx (columns + renderer)
- - features/students/pages/StudentsPage.tsx (custom page layout)
-
- Total: ~200 lines of custom code per table
- Problem: This repeats for Teachers, Orders, etc.
-
- AFTER (New Architecture):
- - features/students/config/student.table.config.ts (ONE config file)
- - features/students/pages/StudentsTablePage.tsx (ONE line: <TablePage ... />)
-
- Total: ~50 lines of code (config only)
- Reuses: All logic from features/tables
-
- ============================================================================
- ADVANCED PATTERNS
- ============================================================================
-
- 1.  CONDITIONAL RENDERING IN MAPPER
-
- mapper: (backend) => ({
-      ...data,
-      displayStatus: backend.status === "ACTIVE" ? "✓ Actif" : "✗ Inactif",
- })
-
- 2.  COMPLEX RENDERING IN RENDERCELL
-
- renderCell: (item, key) => {
-      if (key === "status") {
-        return (
-          <Badge variant={item.status === "ACTIVE" ? "success" : "danger"}>
-            {item.displayStatus}
-          </Badge>
-        );
-      }
- }
-
- 3.  CUSTOM INITIAL FILTERS
-
- <TablePage
-      config={config}
-      initialFilters={{ status: "ACTIVE" }}
-      title="Active Users"
- />
-
- 4.  DYNAMIC COLUMNS (you could extend TableConfig)
-
- export interface DynamicTableConfig extends TableConfig {
-      getColumns: (user: UserRole) => TableColumn[];
- }
