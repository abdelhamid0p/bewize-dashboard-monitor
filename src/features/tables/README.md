- ============================================================================
- CORE COMPONENTS & THEIR RESPONSIBILITY
- ============================================================================
-
- 1.  TableConfig<TBackend, TUI, TFilters> (types/table-config.ts)
- ──────────────────────────────────────────────────────────────────
- Purpose: Type definition for table configuration
-
- Contains:
-      - entityName, tableId, pageSize
-      - columns (display definition)
-      - filters (available filters)
-      - searchKeys (searchable fields)
-      - fetcher (API call)
-      - mapper (backend → UI transformation)
-      - renderCell (custom JSX per column)
-
- Generic parameters:
-      - TBackend: Type from API response
-      - TUI: Type for display
-      - TFilters: Type for filter state
-
- 2.  useTableData Hook (hooks/useTableData.ts)
- ──────────────────────────────────────────
- Purpose: Manage all table state and logic
-
- Handles:
-      - Fetching data with filters
-      - Pagination state
-      - Search state
-      - Filter state
-      - Loading/error states
-      - Data transformation (mapper)
-      - Auto-refetch on dependency changes
-
- Returns:
-      - data: Transformed UI items
-      - loading, error states
-      - pagination info
-      - updateFilters, goToPage, setSearchTerm functions
-
- 3.  GenericDataTable Component (components/DataTable.tsx)
- ──────────────────────────────────────────────────────
- Purpose: Render table with pagination controls
-
- Props:
-      - config: TableConfig object
-      - tableState: UseTableDataResult from useTableData
-
- Handles:
-      - Loading/error display
-      - Table rendering
-      - Pagination buttons
-      - Custom cell rendering
-
- 4.  TableToolbar Component (components/TableToolbar.tsx)
- ────────────────────────────────────────────────────
- Purpose: Render search input and filter controls
-
- Props:
-      - config: TableConfig object
-      - tableState: UseTableDataResult from useTableData
-
- Handles:
-      - Search input
-      - Filter dropdowns/inputs
-      - onChange handlers
-
- 5.  TablePage Component (pages/TablePage.tsx)
- ─────────────────────────────────────────
- Purpose: Main page layout combining everything
-
- Props:
-      - config: TableConfig object
-      - title: Page title
-      - showExport, showSettings: Boolean flags
-      - initialFilters: Starting filter values
-      - headerActions: Custom header buttons
-
- Composition:
-      - Header (title + export + settings buttons)
-      - TableToolbar (search + filters)
-      - GenericDataTable (table + pagination)
-
- This is THE COMPONENT to use in your page!

- // features/teachers/config/teachers.table.config.ts
- import { TableConfig } from "@/features/tables";
- import { fetchTeachers } from "../api/teachers_api";
- import type { TeacherBackend, TeacherUI, TeachersFilters } from "../model";
-
- export const TEACHERS_TABLE_CONFIG: TableConfig<
-     TeacherBackend,
-     TeacherUI,
-     TeachersFilters
- > = {
-     entityName: "Teachers",
-     tableId: "teachers-table",
-     pageSize: 10,
-
-     columns: [
-       { key: "name", label: "Nom" },
-       { key: "subject", label: "Matière" },
-       { key: "actions", label: "Actions" },
-     ],
-
-     filters: [
-       {
-         key: "subject",
-         label: "Subject",
-         type: "select",
-         options: [
-           { label: "Maths", value: "MATH" },
-         ],
-       },
-     ],
-
-     searchKeys: ["name", "subject"],
-
-     fetcher: fetchTeachers,
-
-     mapper: (backend) => ({
-       id: backend.id,
-       name: `${backend.firstName} ${backend.lastName}`,
-       subject: backend.subject,
-     }),

-     renderCell: (teacher, columnKey) => {
-       switch (columnKey) {
-         case "name":
-           return <strong>{teacher.name}</strong>;
-         default:
-           return teacher[columnKey];
-       }
-     },
- };

- ============================================================================
- BENEFITS & WHY THIS APPROACH
- ============================================================================
-
- 1.  ELIMINATES DUPLICATION
- ├─ Old way: 150+ lines per table × 10 tables = 1500+ lines
- └─ New way: 120 lines config + 290 lines shared = 410 lines
-
- 2.  TYPE SAFETY
- ├─ Every column, filter, mapper is type-checked
- ├─ Compiler prevents mismatched types
- └─ Refactoring is safe (rename field = compile errors alert you)
-
- 3.  CONSISTENCY
- ├─ All tables work the same way
- ├─ Same pagination behavior
- ├─ Same search/filter behavior
- └─ Bug fix = all tables get it automatically
-
- 4.  SCALABILITY
- ├─ Adding 10th table = ~100 lines of new code
- └─ If old way = 150+ lines per table
-
- 5.  MAINTAINABILITY
- ├─ Fix pagination bug = 1 file change, not 10
- ├─ Add new filter type = 1 component change, not 10
- └─ Change API response format = 1 mapper, not 10
-
- ============================================================================
- PATTERNS & BEST PRACTICES
- ============================================================================
-
- 1.  Organizing Config Files
- - Put config in entity's config/ folder
- - Keep enums/constants with config
- - Example: student.table.config.ts with GENDER_CONFIG, CYCLE_CONFIG
-
- 2.  Mapper Complexity
- - Mapper is for DATA TRANSFORMATION only
- - Don't put business logic in mapper
- - Example: format dates, join names, map enum values
- - renderCell is for DISPLAY logic (styling, components)
-
- 3.  Custom Rendering
- - Use renderCell for JSX
- - Use mapper for simple data transforms
- - Not everything needs renderCell (basic string render is default)
-
- 4.  Filters Configuration
- - Each filter must have a key that exists in TFilters
- - Filters are optional - don't add if not needed
- - Type safety: filterKey must match TFilters property
-
- 5.  Search Implementation
- - List searchable fields in searchKeys array
- - Keys must be properties of TUI type
- - Search is simple string matching (extend if needed)
-
- ============================================================================
- WHEN NOT TO USE THIS ARCHITECTURE
- ============================================================================
-
- This architecture is for TABLE-BASED UIs. Consider alternatives if:
-
- ❌ Need inline editing
- ❌ Complex multi-select interactions
- ❌ Drag-and-drop reordering
- ❌ Highly specialized layout
-
- But even then: extend TableConfig first before creating alternatives!
-
- ============================================================================
- EXTENDING THE ARCHITECTURE
- ============================================================================
-
- If you need advanced features:
-
- 1.  ROW ACTIONS
- - Add extra column with key="actions"
- - Use renderCell to return action buttons
- - Example: <StudentsActionsMenu studentId={student.id} />
-
- 2.  SORTING
- - Extend TableConfig with sortBy field
- - Pass sort param to fetcher
- - Update useTableData to handle sorting
-
- 3.  BULK ACTIONS
- - Add checkbox column
- - Extend useTableData with selection state
- - Add action bar above table
-
- 4.  INLINE EDITING
- - This breaks the pattern - consider separate EditForm
- - Or: renderCell returns editable inputs
- - Update API on blur/enter
-
- ============================================================================
- TROUBLESHOOTING
- ============================================================================
-
- Problem: Data not loading
- → Check fetcher function, ensure it returns PaginatedResponse
- → Verify API endpoint and parameters
-
- Problem: Filters not working
- → Filter key must exist in TFilters interface
- → Fetcher must handle filter params
-
- Problem: Pagination showing wrong numbers
- → API response.meta must have: page, size, totalPages, totalElements
-
- Problem: Custom rendering not showing
- → Check renderCell columnKey matches actual column key
- → renderCell is optional, ensure you're returning JSX
-
- Problem: TypeScript errors
- → Check mapper return type matches TUI
- → Check column keys exist in TUI
- → Check searchKeys are keyof TUI
